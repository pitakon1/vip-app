# 「发现」Tab 定位调研与改版建议（2026-11-16）

> 范围：`mobile-app`（Expo / React Native）C 端底部导航。
> 本轮只做调研与建议，**未改动任何页面代码**。
> 结论以现有代码与接口为准；行业部分标注了可信度，低可信项已在文中注明「待人工核对」。

## 0. 结论摘要

1. 现在「发现」页 5 个模块里有 **2 个与首页直接重复**（国际学校 rail、楼盘/小区 rail），1 个控件重复（城市选择），1 个模块只有数量没有决策价值（市场速览 4 统计）。
2. 国内外主流房产 App **基本没有「发现/行情」这个 tab**；第 4/5 个 tab 通常是「消息」和「我的 / 我的家（资产与服务）」，行情类内容放在首页模块或详情页。
3. 本项目是**租赁 + 资产管理**产品（不是纯信息门户），真正缺的不是「内容」，而是**办事入口**：账单、报修、合同、委托、收益。
4. **推荐方案 A：把第 2 个 tab 改为「服务」**（租客 / 业主按角色自适应），并把「我的」收敛为账号与设置；「区域均价」这类差异化行情降级为首页一个模块（方案 B 的轻量版），不做独立 tab。

## 3. 行业调研：底部导航怎么分工

> 说明：tab 标签与顺序来自各 App 当前公开版本（App Store 描述、官方产品介绍、公开测评）。App 版本迭代会调整，涉及具体顺序的条目标注了可信度；无标注者为高可信。

### 3.1 国内

| 产品 | 底部 Tab（典型） | 第 4/5 个 tab 放什么 | 关键观察 |
|---|---|---|---|
| 贝壳找房 | 首页 / 找房 / **我家** / 消息 / 我的 | 「我家」= 与我相关的资产与服务：我的小区行情、我的房子、租约/交易进度、装修服务；「消息」= IM + 系统通知 | 第 3 位不是内容，而是**个人资产中枢**；行情只作为「我家」里的一个子模块出现 |
| 链家 | 首页 / 找房 / 消息 / 我的（部分版本含「我家」） | 消息、我的 | 与贝壳同源，无「发现/行情」tab |
| 安居客 | 首页 / 找房 / 消息 / 我的 | 消息、我的 | 4 tab，内容型模块（资讯、榜单）全部堆在首页信息流 |
| 自如 | 首页 / 找房（或租约）/ 消息 / 我的（版本差异较大，**待人工核对**） | 消息、我的；租约/账单被抬到第二中心 | 服务型租赁产品把「我的租约/账单」当成高频入口，而不是把「资讯」做成 tab |

### 3.2 海外

| 产品 | 底部 Tab（典型） | 第 4/5 个 tab 放什么 | 关键观察 |
|---|---|---|---|
| Zillow | Home / Search / Saved / Updates(Inbox) / More | 收藏与更新提醒、消息、更多 | 2026 年 Zillow 上线「buyer hub」把**从搜索到成交的全流程**做成个性化中枢（官方新闻稿 2026-06-23），方向是「交易进度」而非「内容频道」 |
| Redfin | Search / Saved / Inbox / More（**待人工核对**当前版本命名） | 收藏、消息 | 强交易链路产品，同样没有行情 tab |
| Rightmove | Search / Saved / My Rightmove / More | 「My Rightmove」= 我的房产、搬家/抵押贷款服务、交易进度 | 第 3/4 位是**服务与交易进度** |
| PropertyGuru（SG/东南亚） | Home / Search / Saved / Inbox / Profile | 收藏、消息 | 资讯/指南（Property Guides、AskGuru）是首页模块与独立内容页，不进底部 tab |
| Dot Property / Hipflat / DDproperty（泰国） | 以 Search / Map / Saved / Chat 为主（3-4 个，**待人工核对**各家最新版本） | 地图、收藏、联系中介 | 泰国本地产品更强调「地图 + 直接联系中介」，内容频道很弱 |

### 3.3 归纳出的三条规律

1. **底部 tab 只放「任务」不放「内容」**：找房、消息、我的/我的家。资讯、行情、榜单属于首页模块或详情页上下文。
2. **第 4/5 位普遍是「与我有关的东西」**：我的资产、我的交易、我的服务进度。这正是本项目已有但散落在「我的」里的能力。
3. **纯数字型的「市场速览」在头部产品里通常不单独成页**，而是变成「我所在小区/我关注的区域」的对比卡片，带趋势与动作。

## 4. 候选方案

> 共同前提：C 端目前 4 个 tab（首页/发现/消息/我的）。以下方案都假设**只替换第 2 个 tab**，不动首页、消息、我的的结构（「我的」内部收敛见方案 A 的迁移说明）。

### 方案 A（推荐）：第 2 个 tab 改为「服务」

**放什么**（按角色自适应，一个页面两种内容）：

- 租客：账单缴费（`Payments`）、报修（`TenantMaintenance`）、我的合同/电子签（`MyContracts`）、文档（`Documents`）、增值服务（`TenantServices`）、我的租约（`MyLease`）
- 业主：委托出租/绑定房产（`PropertyBinding`）、我的房产（`OwnerProperties`）、收益明细（`OwnerIncome`）、维修审批、营销推广（`OwnerMarketing`）、业主服务（`OwnerServices`）

**与首页如何区分**：首页回答「住哪儿/买哪儿」（找房），服务回答「我的房子现在要办什么」（办事）。首页的「最近动态」只保留 1-2 条提醒并跳转到服务 tab 的对应条目，不再承担完整办理。

**复用**：页面 100% 已存在，只需新建一个聚合页（分组卡片 + 角标数字），复用现有 `navigation.navigate` 目标；数据可直接复用各页面已封装的接口（账单列表、工单列表、租约、合同）。

**迁移成本**：低。新增 1 个 screen + 1 个 tab 配置项 + i18n 文案；`ROLE_TABS` C 端改一行。

**风险**：
- 与「我的」现有入口重复（Profile L123-L140 已列了账单/报修/合同/服务/文档）→ **必须同步把「我的」收敛为账号、设置、收藏/足迹、价格提醒**，否则从「重复的发现页」变成「重复的服务页」。
- 服务 tab 需要角标（待缴账单数、待处理工单数），否则用户感知不到新消息；角标接口需要合并 2-3 个统计。

### 方案 B：保留「行情」但做深，不做列表

**放什么**：区域均价趋势（近 6/12 个月）、区域对比（自选 2-3 个区）、小区价格榜（涨幅/成交活跃）、汇率（`exchangeRates`）、学校分布与通勤（`geo/distance` + 学校数据）。

**与首页区分**：首页给「房源卡片」，行情给「判断依据」（趋势、对比、榜单），两者不共用卡片形态。

**复用**：`listingCategorySummary`（已有 `district_price_pairs`）、`districts()`、`projects()`、`schools()`、`exchangeRates()`、`/geo/distance`。

**迁移成本**：中。需要后端补「时间序列均价」（当前只有当期均价），否则只能做静态对比，价值有限。

**风险**：C 端用户（租客为主）对行情低频；数据供给不足时页面会显得空；与首页「新房 rail」的边界需要严格约束（行情页不出现房源列表）。

### 方案 C：「地图找房」tab

**放什么**：地图 + 聚合点 + 画圈找房 + 列表联动。

**复用**：后端 `/public/map-points`、`/geo/*` 已就绪。

**迁移成本**：高。App 目前**没有任何地图渲染组件**（未装 `expo-maps` / `react-native-maps`，见 `src/config/maps.ts` 注释），需要新增原生依赖、`app.json` 平台 Key、Android SHA-1 / iOS Bundle ID 限制；且 Google Maps 结算尚未生效。

**风险**：最高（新原生依赖 + 重新打包 + Key 限制未完成 + Billing 未恢复）。建议等地图 Key 应用限制补齐、Billing 生效后再单独立项。

### 方案 D：「工具」tab

**放什么**：汇率换算、通勤/学校距离测算、租金收益率计算器、合同模板下载、报修指南。

**复用**：`exchangeRates`、`geo/distance`、`Documents`。

**迁移成本**：低（页面轻），但**内容供给薄**，多数工具使用频次极低。

**风险**：tab 位是稀缺资源，放低频工具不划算；更适合作为服务 tab 里的「小工具」区块。

### 方案对比

| 维度 | A 服务 | B 行情 | C 地图找房 | D 工具 |
|---|---|---|---|---|
| 用户频次 | 高（账单/报修/合同） | 低-中 | 中（找房期） | 低 |
| 与首页差异 | 强（办事 vs 找房） | 中（判断 vs 房源） | 中（空间 vs 列表） | 弱 |
| 复用现有页面 | 100% | 60%（缺趋势数据） | 30%（需装地图库） | 70% |
| 开发成本 | 低 | 中 | 高 | 低 |
| 风险 | 中（需同步收敛「我的」） | 中（数据供给） | 高（原生依赖 + Key） | 低但价值低 |

## 5. 推荐方案与理由

### 推荐：方案 A「服务」tab + 方案 B 的轻量版（区域均价留在首页）

理由：

1. **产品定位决定**：本项目是「租赁 + 资产管理」，不是信息门户。租客高频动作是缴费/报修/看合同，业主高频动作是收益/委托/维修审批——这些现在都能做，但被埋在「我的」二级入口里。
2. **行业验证**：贝壳「我家」、Rightmove「My Rightmove」、Zillow buyer hub 都在把「与我有关的交易与服务」抬到主 tab；没有任何一家把纯行情做成主 tab。
3. **成本最低、收益最直接**：所有目标页面都已存在，只需要一个聚合页和角标，不新增原生依赖，不依赖未生效的 Google Maps Billing。
4. **顺手解决重复问题**：「发现」整页下线，重复块自然消失；同时把「我的」从「功能列表」收敛为「账号 + 设置 + 收藏足迹」，两个 tab 的边界一次理顺。

### 推荐方案下，「发现」里应当删掉的模块

| 模块 | 处理 | 说明 |
|---|---|---|
| 国际学校 rail（L221-L261） | **删** | 与首页完全重复；学校是找房决策因子，保留首页那个「带学校筛房源」的入口 |
| 热门小区 rail（L173-L219） | **删** | 与首页新房 rail 同一实体、同一卡片族；若未来要做榜单，改为「区域涨幅榜」进行情模块，而不是复刻楼盘列表 |
| 市场速览 4 统计（L136-L148） | **删** | 只有数量、不可点、无趋势，属于「看起来有数据」的装饰；日均访问价值低于改造成本 |
| Hero 右上城市 chip（L114-L126） | **删** | 城市切换保留首页那一处，避免同一 store 出现两个入口 |
| 区域均价（L150-L171） | **迁移到首页**（放在分类 rail 之上或「最近动态」之上），作为唯一保留的行情能力；后续有历史数据再升级为趋势图 | 这是全页唯一不重复且有决策价值的内容，直接删掉可惜 |

### 需要用户确认的三点

1. 第 2 个 tab 的命名：**服务** / **办事** / **我的家**（贝壳用的是「我家」；本产品业主与租客合一，建议「服务」更中性）。
2. 「我的」是否可以同步精简（把账单/报修/合同/文档/服务/委托 6 个入口移到服务 tab）？不同步精简会出现新的重复。
3. 区域均价迁到首页的具体位置（建议放在 7 磁贴之后、分类 rail 之前）。

### 建议实施顺序（待确认后执行）

1. 新建 `ServiceScreen`（聚合页，按角色渲染两组卡片，带待办角标）
2. `MainTabNavigator` C 端第 2 项改为 `Service`（icon 建议 `grid` / `construct`）
3. Profile 移除已迁走的 6 个入口，保留账号/设置/收藏/足迹/价格提醒
4. 首页新增「区域均价」模块（复用 `listingCategorySummary`）
5. 下线 `DiscoverScreen` 及其 i18n 文案（`discover.*`）
