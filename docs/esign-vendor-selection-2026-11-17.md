# 外部电子签产品选型与可行性调研

> 版本：2026-11-17（v2）
> 背景：决定放弃 pyHanko 自建电子签，改为采购外部电子签产品（候选 e签宝）。
> 场景：平台把租房/买卖/经纪合同签给**泰国用户**，签约主体未定。
> **v2 新增两条硬约束**（据此重排结论，对比表保留）：
> 1. 签署人同时包含中国用户与泰国用户，需要中/英/泰多语言界面与中泰双语身份核验；
> 2. 采购主体是**泰国公司**，合同、发票、付款均走泰国实体，因此受泰国 PDPA 约束，个人数据出境（含出境到中国）需额外合法依据。
> 口径：只写官方来源可核的内容；未核到的标「待核实」，价格一律不猜。

---

## 0. 结论摘要

| 问题 | 结论 |
| --- | --- |
| 硬约束（v2） | ① 泰国公司主体采购/开票/付款；② 中国+泰国签署人，需中/英/泰界面与中泰双语核验；③ 受泰国 PDPA 约束，数据出境需合法依据 |
| **首选** | **DocuSign（经泰国 SiS Distribution 本地采购）**：泰语签署界面（44 语）、API/Connect 最成熟、泰国本地采购渠道可解决主体与发票；但数据中心只有 US/CA/EU/AU/JP，**无泰国/新加坡**，PDPA 出境依据与泰籍证件核验必须落实 |
| **备选** | **腾讯云电子签 国际版（新加坡节点）**：核心数据中心在新加坡，泰语 Web 签署页、中文界面、大陆身份证/护照 + 人脸、API 完整、公开价；泰国主体开户/发票与泰籍身份证待核实 |
| **不建议** | **e签宝 / eSignGlobal**：签约主体为香港实体、无泰国节点、泰文界面未获官方证实、护照仅支持银行卡核验 → 三条硬约束均不满足 |
| 观察名单 | 法大大 Nota Sign（唯一官方列泰语，但泰国主体/数据节点/泰籍核验未核实）；Adobe Acrobat Sign（数据仅 US/JP/AU/IN，泰籍 IDV 未列）；Dropbox Sign（无泰国节点，标准版仅邮箱验证） |
| 泰国本地 | INET、TDID 是 NRCA 体系 CA，不提供企业级 SaaS 签署 API；DGA D-SIGN 仅限政府机关 → 暂无可选产品 |
| API 完整度（e签宝） | 完整：`/v3/sign-flow/create-by-file`、`start`、签署链接、`notifyUrl`、归档下载、申请出证；但海外模式需专业版及以上 |
| 最大风险 | 泰籍身份证核验、泰国税务发票（VAT）、数据出境依据（或泰国本地驻留）——三项都必须供应商书面确认 |

| 能力 | 内容 | 状态 |
| --- | --- | --- |
| 个人认证覆盖人群 | 官方产品页：面向**大陆、港澳台、少数民族及外籍人士**，按业务安全等级组合姓名、证件号、手机号、人脸等要素 | 已核实 |

**判断**：能力矩阵是齐的，但"护照只能银行卡认证"这条如果同样适用于海外签，会直接影响泰国用户的签署转化率。必须让销售给出**泰国用户从打开链接到完成签署的完整路径截图**。

### 1.3 语言

### 1.6 发票与合同主体

| 问题 | 结论 | 状态 |
| --- | --- | --- |
| 中国主体签约、开中国增值税发票 | 行业惯例可开，但**未在官方页面核到** → 待核实 | 待核实 |
| eSignGlobal 的签约主体 | 公开资料指向香港实体 **Esign HK Holding Limited**（HKTDC 展商页）；官网未写合同签约主体 → 以香港主体签约可能性高 | 部分核实 |
| **与泰国主体直接签约** | 官方未见泰国实体或泰国分公司；国际业务总部在香港 → **泰国主体直签未见证据，按硬约束判「不适合」** | 待核实（倾向不适合） |
| **泰国税务发票（Thai VAT）** | 未见任何官方说明；香港/中国实体通常无法开具泰国增值税发票 → **不适合**（除非泰国代理由本地伙伴开票，未核实） | 待核实（倾向不适合） |
| **数据是否必须回中国境内** | 官方外企方案：大陆业务用国内数据中心，**纯境外业务用海外数据中心**；海外签落在 HK/SG/法兰克福 → **不强制回中国**，但也不在泰国 | 已核实（官方外企方案页） |
| **泰文界面** | 官方只明示"中英文等多语言界面，外籍可切英文"；**泰语未见官方语种清单** → 待核实（按现有证据不足以满足硬约束） | 待核实 |
| **泰国签署人核验** | 护照：手机❌、人脸❌、银行卡✔（中国站口径）；泰国本地银行卡是否可用于该通道未见说明 → **不能作为泰籍用户主通道** | 已核实口径；适用性待核实 |
| 发票币种/形式 | 未见官方说明 → 待核实 | 待核实 |
| 是否需要企业实名 | 企业认证能力存在（见 §1.2），但是否为开通前置条件 → 待核实 | 待核实 |

## 2. 国内同类厂商对比

| 厂商 | 境外 / 多语言能力 | 状态 |
| --- | --- | --- |
| **法大大（Nota Sign 全球签）** | 独立国际版产品；官方定价页明确支持 **9 种语言：英、简中、繁中、西、**泰**、俄、葡、越、印尼**；适配 100+ 国家；全球分布式数据中心；7 天试用 20 个信封 | 已核实（语种与试用）；价格需询价 |
| **腾讯电子签** | 有"海外签"：签署通知支持短信，可按签署方指定语言（简中、繁中、English、**泰语**、越南语、马来语、印尼语）。但官方 FAQ 又写"与中国内地以外个人签署的功能**正在开发中**" → **两处口径冲突，必须向销售确认** | 已核实（两处原文）；实际能力待核实 |
| **上上签** | 有国际版；官方新闻称支持英语、日语、简体中文等多语言，覆盖海外本土签/跨国签 | 已核实（官方新闻）；**泰语支持待核实** |

**一句话**：

- 法大大 Nota Sign 是**唯一在官网页面上把泰语写进支持列表**的国内产品。
- 腾讯电子签的海外签能力存在**官方口径冲突**，不能仅凭更新日志判断可用。
- 上上签国际化最早，但语种清单未覆盖泰语证据。

**v2 复核补充（重要）**：腾讯电子签的"海外签"在国内站与国际站是两条产品线。国际站 **Tencent Cloud eSign** 的产品页写明核心数据中心在**新加坡**，更新日志也写明"海外签 Web 嵌入页面支持泰语"。这与国内站 FAQ"境外个人签署开发中"并不必然矛盾（国内站面向中国主体）。**主体为泰国公司时，应直接评估国际站，详见 §3.2**；国内站口径不作为判据。

> 纠错说明：腾讯云文档中"含曼谷地域、专业版 698 美元/月"的页面属于 **WeData（产品 1174）**，不是电子签。**eSign 没有已确认的泰国/曼谷节点**，不要把该地域当作数据留泰的依据。

**判断**：

- 国际四家技术上都能用，但**没有一个能证明支持泰国身份证核验**，且**中国主体签约/开票**都要单独确认。
- 按"份"计价的区间：DocuSign 开发者档 $40/月起、Dropbox Sign API $75/月起；PandaDoc 是**按席位**（$19/$49）而非按份；Adobe Sign **需询价**。
- 若用户以泰国用户为主、且团队在中国，国际厂商的本地化支持（泰语、泰国支付、中文服务）反而是短板。

| 厂商 | 数据存放区域（官方） | 泰文界面 | 泰国身份证 / 护照核验 | 与泰国主体签约 / 开票 | 按份计价口径 |

| **Adobe Acrobat Sign** | 官方 JAPAC 子处理者页：Acrobat Sign 处理地域 **US / Japan / Australia / India**；系统要求页出现的新加坡地址是接入/回调 IP，不等于存储区域 | 支持**泰语**（官方语言版本列表） | Government ID 认证按国家列表，**未见泰国** → 大概率不支持，待核实 | Adobe 实体签约；泰国可经本地代理采购，Thai VAT 待核实 | 需询价 |

| PDPA | 数据在新加坡 → **仍属泰国出境**，需第 28 条依据；只有数据确实不出泰国才不构成跨境 | 需法务确认 |

### 3.3 泰国本地服务商

| 主体 | 性质 | 能否满足"API 电子签 SaaS" | 状态 |
| --- | --- | --- | --- |
| **INET CA**（Internet Thailand PCL） | NRCA 体系 CA，签发个人/组织/服务器证书 | 官网只提供证书签发，**未见 SaaS 签署 API** → 不能单独满足 | 已核实（其 CA 页面） |
| **TDID**（Thai Digital ID） | NRCA 体系 CA，税务局认可的数字签名证书提供方 | 以证书为主；是否提供 SaaS 签署 API **待核实** | 部分核实 |
| **NTCA / TKC / ETSA** | NRCA 体系 CA / TSA | 证书或时间戳，不是签署 SaaS | 已核实（NRCA 名单） |
| **DGA D-SIGN** | 泰国政府数字政务平台 | **仅政府机关使用，私营企业不可用** | 已核实 |
| 其他本地 SaaS | 未检索到"ETDA/NRCA 认证 + 公开 API + 中泰双语"的成熟产品 | — | 待核实 |

**结论**：泰国本地有合规 CA/TSA，但**没有找到可直接替代外部电子签 SaaS 的企业级 API 产品**。本地 CA 更适合作为"QES 证书/时间戳"的合规补充，而不是整条签署链路。

## 4. 法律与合规

> 本节只陈述条文与监管事实，**适用结论一律需法务确认**，工程侧不做判断。

### 4.1 泰国《电子交易法》（Electronic Transactions Act）

| 要点 | 内容 | 状态 |
| --- | --- | --- |
| 法律版本 | ETA B.E. 2544（2001），经 B.E. 2562（2019）修订 | 已核实（ETDA 官方与法律解读） |

| 实务分级 | 市场通常分为 Type 1（一般电子签名）、Type 2（第 26 条 PKI）、Type 3（第 28 条 CA 认证） | 已核实（第三方法律解读，非官方，仅作参考） |
| 租房合同是否可用 SES | **需法务确认**（不同合同类型、是否需登记、双方是否约定更高等级） | 需法务确认 |

| 要点 | 内容 | 状态 |
| --- | --- | --- |

### 5.2 需要新增的适配层

```
EsignProvider（接口）
├─ create_flow(contract, parties, file_bytes) -> {flow_id, sign_urls}
├─ parse_callback(headers, raw_body) -> NormalizedEvent   # 验签 + 幂等
├─ fetch_artifacts(flow_id) -> {signed_pdf, evidence_report, cert_chain}

```

配套数据变更（建议）：

- `Contract.provider`（`internal` / `esign` / `fadada` / ...）、`provider_flow_id`
- `Contract.provider_status`（与本地 `ContractStatus` 映射）
- `SignatureRecord` 增加 `provider`、`provider_signer_id`、`evidence_ref`、`signed_file_hash`
- 新表 `EsignCallbackEvent`（入站）：原始报文快照、验签结果、幂等键、处理状态——**不要复用出站的 `ContractCallbackEvent`**，两者方向与重试语义不同

入站回调要点：

1. 独立路由 `POST /api/v1/esign/callback/{provider}`，**不走登录鉴权**，改用供应商签名/密钥验签；
2. 先落原始报文，再解析，避免解析失败丢失证据；
3. 幂等键用供应商 `flow_id + event`；
4. 处理失败可重试，且能被后台补拉任务兜底；
5. 回调只做"状态推进 + 触发下载"，**不要**在回调里同步做大文件下载。

### 5.3 接入形态：三端可行性

| 端 | 推荐形态 | 可行性 | 说明 |
| --- | --- | --- | --- |
| Web（frontend-web） | **H5 跳转**（新标签或同页跳转签署链接） | ✅ 最稳 | 供应商签署页通常禁止被 iframe 嵌入（X-Frame-Options/CSP），**内嵌需供应商确认 → 待核实** |
| 小程序（miniapp） | **短信/服务通知带链接 + 外部浏览器打开**，首期不做内嵌 | ⚠️ 受限 | 微信小程序 `web-view` 只能打开**已配置业务域名**（需域名归属校验），无法直接加载供应商域名；小程序插件是否存在 **待核实** |
| App（React Native / Expo） | `expo-web-browser` 打开签署链接 + deep link 回跳 | ✅ 可行 | 需处理"签署完成回跳 App 后刷新状态"；回调仍以服务端 webhook 为准 |

统一原则：**不要依赖前端回跳判断签署完成**，一律以服务端回调 + 主动查询为准。

### 5.4 数据归属与回传落库

| 数据 | 谁保存 | 我们的动作 |
| --- | --- | --- |
| 带签 PDF | 供应商 + 我们 | 回调后立即下载，存私有对象存储；库内存 `signed_file_hash` |
| 存证报告 / 出证材料 | 供应商 | 下载归档；只存引用 ID，不依赖在线 URL（可能过期或需登录） |
| 审计轨迹（查看/签署/IP/时间） | 供应商为主 | 拉取关键节点落库，供我们自己的审计页展示 |
| 人脸/证件影像 | **仅供应商** | 我们只存"核验通过/失败"结果与凭证引用，**不落原始影像**（PDPA 最小化） |
| 供应商侧保留期限 | 供应商 | **待核实**；不要对外承诺"永久保存" |
| 存储区域 | 供应商（按合同） | 选新加坡节点时仍需出境依据；若供应商能证明数据（含备份、日志、子处理者）不出泰国，写入 DPA；选 DocuSign 时按 PDPA 第 28/29 条准备出境依据（**需法务确认**） |

### 5.5 迁移：历史已签合同

1. **不重签**。已签 PDF 的签名依赖当时的证书与时间戳，重签会破坏原签名与交付版本。
2. **保留旧 CA 材料**：`ca_cert.pem`、`ca_key.pem`、`ca.pfx` 归档封存（验签只需证书，私钥封存即可）。
3. **验签双通道**：`Contract.provider = internal` 的走本地 `verify_pdf`；新合同走供应商。页面明确标注"平台自签（2026-11 前）"。
4. **旧签署链接下线**：`contract_sign_public.py` 的公开入口改为只读或 410，避免旧链接继续产生新签名。
5. **旧 TSA 记录保留**：若历史合同曾启用时间戳，保留 TSA 根证书与当时的验签结果快照。
6. **审计连续性**：迁移前后都要能回答"这份合同是谁、什么时候、用什么方式签的"。

## 6. 结论

### 6.1 首选 / 备选 / 不建议（按 v2 硬约束重排）

**首选：DocuSign（经泰国 SiS Distribution 本地采购）**

| 硬约束 | 满足方式 | 确定性 |
| --- | --- | --- |
| 泰国主体采购/开票/付款 | SiS 官网有 DocuSign 产品页并引导本地渠道采购，泰国实体可本地下单 | 中高（授权关系、Thai VAT 需书面确认） |
| 中英泰界面 | 签署界面 44 语含泰语，中国用户可切简中；管理端仅 14 语（无泰语） | 高（签署端）；管理端不足 |
| 中国+泰国签署人核验 | IDV 支持政府照片证件 + 欧洲 eID；护照路径可用；泰国身份证未列 | 中（泰籍证件待 POC） |
| PDPA 数据出境 | 数据中心 US/CA/EU/AU/JP，无泰国/新加坡 → 必须走第 28 条合法路径 | 需法务确认 |
| API/Webhook | REST API + Connect Webhook 最成熟 | 高 |

**取舍**：它是唯一同时具备"泰国本地采购渠道 + 泰语签署界面 + 成熟 API"的候选；代价是数据只能存澳/日，PDPA 出境依据必须落地，泰籍身份证核验未证实，成本最高。

**POC 验收 5 条（缺一不可）**：
1. 泰国手机号 + 护照 + 人脸完成全流程；
2. 如业务强制，泰国身份证能否核验（否则明确降级为护照）；
3. 签署页、邮件、短信为泰语，且中国用户可切中文；
4. 回调验签机制、幂等键、重放防护；
5. SiS 合同主体、Thai VAT 发票、DPA 出境条款三项书面确认。

**切换规则**：若第 2 条（泰国身份证）不通过且业务强制要求 Thai ID，则改选腾讯云电子签（新加坡节点）；若第 5 条 Thai VAT 无法满足，DocuSign 方案直接不可用，必须回到腾讯或其他本地可开票渠道。

**备选：腾讯云电子签 国际版（新加坡节点）**

- 优势：核心数据中心在**新加坡**（东盟、离泰国近）；泰语 Web 签署页 + 中文界面；大陆/香港身份证 + 各国护照 + 人脸；API/模板/信封完整；公开价（海外签 Premium **$300/套/年**、Professional **$3,999/套/年**）。
- 取舍：新加坡仍属泰国出境，PDPA 依据不可省；泰国主体开户与 Thai VAT 未证实；泰籍身份证是否已接入 eSign 待 POC；全球法律认可度弱于 DocuSign。
- 适用：预算敏感、中国签署人占比高、能接受新加坡出境。

**不建议：e签宝 / eSignGlobal（在当前约束下）**

| 硬约束 | 实际情况 | 判定 |
| --- | --- | --- |
| 泰国主体采购/开票 | 国际业务主体为香港实体；未见泰国实体或 Thai VAT 能力 | **不适合** |
| 中英泰界面 | 官方只明示中/英文；泰语未证实 | 不满足 |
| 泰籍签署人核验 | 护照仅支持银行卡认证，手机/人脸均不支持 | **不适合** |
| PDPA | 数据落在 HK/SG/法兰克福，仍需出境依据，且无泰国节点 | 不占优 |

结论：**不适合作为"泰国主体 + 泰籍用户"的主方案**。若未来主体改回中国/香港、且签署人以中国籍为主，可重新评估——它的 API 与国内服务能力本身没有问题。

**其余**：
- 法大大 Nota Sign：泰语确定，列观察名单；泰国主体、数据节点、泰籍核验均未核实。
- Adobe Acrobat Sign：泰语有，但数据仅 US/JP/AU/IN，Government ID 国家表未见泰国 → 不建议。
- Dropbox Sign：泰语有、价格低，但无泰国节点、标准版仅邮箱验证 → 不建议作为主方案。
- 泰国本地 CA（INET/TDID/NTCA/TKC）：只能作为 QES 证书/时间戳补充，不是签署 SaaS。

**接入形态（三端）**：

- Web：**H5 跳转**为首选；iframe 仅在供应商书面允许时使用（腾讯海外签有"Web 嵌入页面"，DocuSign 有 embedded signing，均需确认是否允许第三方域名嵌入）。
- 小程序：`web-view` 只能打开已配置业务域名，无法直接加载供应商域名 → 首期走"短信/服务通知 + 外部浏览器"。
- App：`expo-web-browser` 打开签署链接 + deep link 回跳；**完成判定只认服务端回调**，不认前端回跳。
