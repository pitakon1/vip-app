# 合作伙伴赋能路线图

> 目标：让合作经纪公司从「用平台的工具干活」升级为「在自己的后台做数字化管理」——
> 看经营、管团队、对佣金、协同房源与客户，平台不介入其内部管理成本。
>
> 适用范围：`role = partner_admin`（合作公司管理员）及其旗下 `role = agent, user_type = partner` 的成员。
> 编写依据：当前仓库代码实况（非设想）。所有「现状」均可对应到具体文件。

---

## 一、定位与判断

### 1.1 现有能力边界

| 层面 | 现状 | 依据 |
|---|---|---|
| 合作管理员菜单 | 仅「成员管理」「考勤」两项 | `frontend-web/src/config/roleMenus.ts` L312-L330 |
| 成员 | 创建（agent）、拉入已注册经纪、移除 | `backend/app/api/v1/partner_members.py` L97-L233 |
| 业绩 | 仅 `/partner/performance` 聚合接口，无独立页面、无明细、无导出 | `partner_members.py` L236-L305 |
| 房源 | 只能看本公司成员 `created_by` 的房源，拿不到平台房源池 | `partner_members.py` L308-L338 |
| 考勤 | 本公司考勤核对 / 按公司 / 考勤组 / 请假审批 / 报表 | `AttendanceManage/index.tsx` L32-L48 |
| 佣金 | 结算表有 `partner_id`，但合作端无结算单、无规则视图 | `models/commission_settlement.py` L48-L82 |
| 合同 / 租约 | 无 partner 维度字段，合作公司不可见 | `models/contract.py`、`models/lease.py` |
| 旗下成员（agent） | 已拥有完整一线工作台：房源、我的房源、线索、租约、合同、聊天、业绩、考勤 | `roleMenus.ts` agent 段 |

### 1.2 核心结论

- **一线作业工具已经齐备**，合作公司的经纪人在平台上是完整的 `agent`。
- **缺的是公司级经营与治理面**：老板看不到经营盘、管不了账号生命周期、对不了佣金账、拿不到平台货源。
- 因此本路线图的重心不是再造业务功能，而是把**已有的数据资产**（结算、支付、考勤、员工、房源）按「合作公司」这个维度组织成管理界面，并补少量缺失的关系字段。

## 二、能力缺口总览

| 编号 | 模块 | 合作公司现在能否自助 | 缺口 |
|---|---|---|---|
| A | 经营驾驶舱与佣金对账 | 否 | 无看板页面、无结算明细、无导出 |
| B | 成员与组织治理 | 部分 | 无启停/重置密码/改资料、无团队层级、无批量导入 |
| C | 考勤人事闭环 | 部分 | 外勤与申诉不可审批、无排班、报表不可导出 |
| D | 房源与客源协同 | 否 | 无平台房源授权代销、无线索池分配、无报备防撞单 |
| E | 交易与履约协同 | 否 | 看不到本公司成交的租约/合同、无续约提醒 |
| F | 公司运营与开放能力 | 否 | 无公告/任务/通用审批、无素材库、无 partner 维度审计与开放接口 |

## 三、分阶段路线图

### 阶段 P0：让合作公司「看得见账、管得住人」

#### A1. 合作公司经营驾驶舱

- **功能**
  - 本月 / 上月核心指标：成交单数、成交额（`commission_base` 汇总）、佣金应收、已结、待结、活跃经纪人、在售房源数
  - 12 个月业绩趋势（复用 `/partner/performance` 的 `month_series`）
  - 经纪人业绩排行、房源贡献排行
- **数据**：`commission_settlements.partner_id`、`payments.partner_id`、`properties.created_by`、`users.partner_id`
- **接口**：`GET /partner/dashboard?month=YYYY-MM`
- **前端**：新增 `/partner/dashboard` 作为 partner_admin 登录默认落地页；菜单置于「成员管理」之前
- **复用度**：高（无新表）
- **验收**
  1. 同一公司数据与 `/partner/performance` 汇总口径一致
  2. 换一家合作公司管理员登录，指标完全隔离
  3. 无成交月份显示 0 而非空态报错

#### A2. 佣金对账单（含导出）

- **功能**
  - 按结算单逐笔列出：成交租约/合同、成交类型、角色、佣金基数、比例、金额、状态（pending / approved / paid）、结算时间、到账时间
  - 期间筛选、状态筛选、按经纪人筛选
  - 导出 CSV / Excel
- **数据**：`commission_settlements`（`partner_id`、`lease_id`、`contract_id`、`status`、`settled_at`、`paid_at`）
- **接口**
  - `GET /partner/settlements?start=&end=&status=&page=`
  - `GET /partner/settlements/export`
- **复用度**：高（无新表；注意只返回 `partner_id = 当前用户` 且 `deleted_at IS NULL`）
- **验收**
  1. 明细求和 = 驾驶舱「佣金应收」卡片
  2. 导出文件字段与页面一致，行数一致
  3. 跨公司 id 直接请求返回 404/403，不泄露存在性

#### A3. 佣金规则只读视图

- **功能**：展示适用于本公司的分成规则（`scope = by_partner` 的专属规则 + 全局规则只读）
- **数据**：`commission_split_rules.partner_id`、`scope`
- **接口**：`GET /partner/commission-rules`
- **验收**：只显示「全局」与本公司的规则；平台侧改规则后刷新可见

#### B1. 成员账号全生命周期

- **功能**
  - 停用 / 启用（`users.is_active`）
  - 重置密码（复用 `get_password_hash`，需审计）
  - 编辑资料：姓名、手机、职位（`employees.position`）
  - 成员详情：角色、入职日期、所属团队、在售房源数、本月业绩
- **接口**
  - `PATCH /partner/members/{user_id}`（仅允许改本公司的 `full_name` / `phone` / `position`）
  - `POST /partner/members/{user_id}/deactivate`、`/activate`
  - `POST /partner/members/{user_id}/reset-password`
- **验收**
  1. 停用后该成员无法登录，且不能再接收新线索
  2. 管理员不能停用自己
  3. 所有写操作落 `partner_id = 当前用户`，跨公司 403

#### B2. 修复现存两处缺陷（随 B1 一并处理）

- `partner_members.py` 创建成员时 `department=current.full_name`（管理员姓名）→ 改为公司名或空
- 创建成功响应 `_serialize_member(new_user, None)` 导致 `position` 恒为 `null` → 传入真实 Employee

### 阶段 P1：让合作公司「组织得起来、人管得全」

#### B3. 团队 / 部门与数据权限

- **功能**
  - 公司内团队（组）的增删改、成员归属
  - 组长角色：只看本组经纪人数据（业绩、考勤、线索）
  - 驾驶舱支持按团队下钻
- **数据方案**：优先复用 `employees.department` + 平台部门表（`Department`），增加 partner 作用域；不新建组织模型
- **接口**：`GET/POST /partner/teams`、`PATCH /partner/members/{id}/team`
- **验收**：组长登录只能看到本组 3 人数据，越权 id 返回 403

#### B4. 批量导入与邀请

- **功能**：CSV 批量开通（姓名/邮箱/手机/职位）；邀请链接注册后自动归属本公司
- **接口**：`POST /partner/members/import`、`POST /partner/invitations`
- **约束**：坐席数上限（见 §5.2）
- **验收**：重复邮箱逐行报错并回显行号，不整批失败

#### C1. 考勤审批闭环补齐

- **功能**
  - 外勤 / 出差申请审批（`ExternalTripApplication` 已存在，合作端未开放）
  - 打卡申诉审批（`AttendanceAppeal` 已存在，当前对 partner 隐藏）
  - 月度考勤报表导出（考勤核对页已有导出按钮，补本公司作用域校验）
- **接口**：`GET /partner/trips`、`POST /partner/trips/{id}/approve`、`GET /partner/appeals`、`POST /partner/appeals/{id}/approve`
- **验收**：跨公司审批 403；审批通过后考勤记录按既有规则落库

#### C2. 排班 / 班次

- **功能**：在考勤组（`work_start` / `work_end`）之上增加「按周排班表」，支持轮班与节假日
- **数据**：新增 `attendance_shifts`（partner_id、employee_id、date、start、end）
- **验收**：排班后的迟到判定以排班时间为准；无排班回落考勤组

#### D1. 平台房源授权代销

- **功能**
  - 平台把指定房源授权给合作公司（可按小区/项目批量授权、可设有效期）
  - 合作公司经纪人可查看授权房源、发起带看、成交计入本公司业绩
  - 授权可撤销，撤销后立即从合作端下架
- **数据**：新增 `partner_property_grants`（partner_id、property_id、granted_by、expires_at、status）
- **接口**：`GET /partner/available-properties`、平台侧 `POST /partners/{id}/grants`
- **验收**
  1. 未授权房源在合作端不可见（列表与详情均 404）
  2. 授权到期自动失效
  3. 产生的成交佣金按 `partner_company` 角色正确结算

#### D2. 线索池分配与报备防撞单

- **功能**
  - 合作公司线索池：管理员把线索分配给经纪人（`leads.assigned_to`）
  - 客户报备：同一客户在保护期内归属首个报备公司，重复报备提示冲突
- **数据**：`leads` 增加 `partner_id`（可空，NULL = 平台线索）；新增 `lead_claims`（客户指纹、partner_id、保护期）
- **接口**：`GET /partner/leads`、`POST /partner/leads/{id}/assign`、`POST /partner/leads/claim`
- **验收**：保护期内跨公司重复报备被拒并给出到期时间

#### D3. 带看任务派发

- **功能**：管理员把 `ViewingAppointment` 指派给经纪人，经纪人回执完成/爽约
- **接口**：`POST /partner/viewings/{id}/assign`、`POST /partner/viewings/{id}/result`
- **验收**：派发后经纪人在 App 端收到待办

### 阶段 P2：让合作公司「协同得顺、接得进系统」

#### E1. 租约 / 合同可见性与续约提醒

- **现状**：`contracts`、`leases` 无 `partner_id`
- **方案**：给 `leases` / `contracts` 增加 `partner_id`（通过 `_ADDITIVE_COLUMNS` 幂等补列），历史数据按 `commission_settlements.partner_id` 回填
- **功能**：本公司成交租约、合同只读视图；到期前 60/30/7 天续约提醒
- **验收**：回填后每笔合作公司成交的租约都能在合作端查到，且不串公司

#### E2. 收款与逾期提醒

- **功能**：本公司相关账单（`payments.partner_id`）状态、逾期列表、催收记录
- **验收**：逾期金额 = 平台侧同口径统计

#### F1. 公告 / 任务 / 固定审批流

- **功能**：公司公告、任务派发与完成回执；折扣、用印、费用三类固定审批（不做通用 BPM 引擎）
- **验收**：任务与审批均按 partner 隔离，且可在 App 端收到

#### F2. 素材库

- **功能**：平台下发的房源海报、话术、培训资料；公司自有素材上传
- **验收**：素材可见范围 = 平台公开 + 本公司

#### F3. 审计与开放能力

- **功能**
  - 合作公司维度操作日志（谁停用了谁、谁改了佣金、谁导出了数据）
  - 开放 API Key / Webhook：成交、佣金状态变更推送
- **验收**：Webhook 至少一次投递、失败重试与签名校验可验证

## 四、权限与数据隔离设计

### 4.1 新增权限点（`backend/app/core/rbac.py` 的 `partner` 分类）

| code | 名称 | 说明 | 默认授予 |
|---|---|---|---|
| `partner:dashboard:view` | 经营看板查看 | 驾驶舱与趋势 | partner_admin |
| `partner:settlement:view` | 佣金对账查看 | 结算单列表与导出 | partner_admin |
| `partner:member:update` | 成员资料编辑 | 启停、资料、职位 | partner_admin |
| `partner:member:reset_password` | 成员重置密码 | — | partner_admin |
| `partner:team:manage` | 团队管理 | 团队增删改与归属 | partner_admin |
| `partner:review:trip` | 外勤审批 | — | partner_admin |
| `partner:review:appeal` | 申诉审批 | — | partner_admin |
| `partner:lead:assign` | 线索分配 | — | partner_admin |
| `partner:grant:view` | 授权房源查看 | — | partner_admin + agent(partner) |

> 现有 `DEFAULT_ROLE_PERMISSIONS[partner_admin]` 仅含 `partner:member:manage`、`data:view`、`attendance:partner:view`，
> 新权限点需同步加入默认分配；`seed_permissions` 幂等补种，不覆盖管理员已有配置。

### 4.2 隔离硬约束（每条新增接口都必须满足）

1. **写操作作用域强制覆盖**：不接受前端传入的 `partner_id`，一律取 `current_user.partner_id`。
2. **读操作强制过滤**：查询条件必须包含 `partner_id = current_user.partner_id`，禁止先查后判。
3. **跨公司访问返回 403/404**：不返回「存在但无权」的差异化信息。
4. **无公司绑定的 partner_admin**：直接 403（沿用 `_partner_guard`）。
5. **停用公司**：`Partner.is_active = false` 时所有合作端接口拒绝（沿用 `_ensure_partner_active`），且旗下账号不可登录。
6. **数据导出**：导出文件仅含本公司数据，且必须落审计日志。

### 4.3 坐席数与合同约束

在 `Partner` 上增加 `seat_limit`（可空 = 不限），创建成员与批量导入时校验。
超限时返回明确错误「已达坐席上限（N），请联系平台扩容」。

## 六、边界与非目标

- **不做多级集团 / 总公司-分公司层级**：合作公司是单层组织，集团需求出现后再评估。
- **不做通用 BPM 引擎**：审批只做固定几类（请假、外勤、申诉、折扣、用印、费用）。
- **不做独立白标站点**：P2 先做公司名称与 Logo 展示；独立域名/主题定制需单独评估成本与运维。
- **平台不做合作公司的发薪与社保**：只做考勤与业绩数据，薪酬计算交给合作公司自有系统（通过导出/API 对接）。
- **佣金口径以平台结算表为准**：合作公司不可自行修改结算金额，只能查看与申诉（申诉入口见后续迭代）。

## 七、待确认问题

1. 合作公司的「佣金应收」应以**结算单生成时点**还是**成交时点**统计？两者口径不同，需要业务确认。
2. 房源授权代销是否需要平台审核合作公司的上架资格（现有 `Broker` 体系有 `listings` 协议，是否要求合作公司先签约）？
3. 线索报备保护期时长（30 / 60 / 90 天）与撞单判定口径（手机号 / 邮箱 / 证件号）？
4. 合作公司是否能创建 `tenant` / `owner` 账号，还是只允许 `agent`？
5. 停用合作公司时，旗下账号是立即禁止登录，还是保留只读一段时间用于导出数据？

## 附录：已知缺陷（非本路线图新增，建议随 P0 修复）

1. `partner_members.py` L161：`department=current.full_name` 把管理员姓名写进员工部门字段，影响按部门统计。
2. `partner_members.py` L169：创建成员返回 `_serialize_member(new_user, None)`，`position` 恒为 `null`。
3. `partner_members.py` L265-L267：`/partner/performance` 中 `settlements` 的查询条件已经限定 `partner_id`，但前置的 `user_ids or employee_ids` 条件在「公司有 settlement 却无成员」时会返回空列表，建议直接以 `partner_id` 判定。
